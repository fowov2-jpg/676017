# ВремяХодом — зафиксированные продуктовые требования

Дата фиксации: 2026-08-17

Этот документ является рабочим ТЗ для текущей ветки `chatgpt/responsive-full-pass-20260817`. Требования ниже считаются обязательными критериями приёмки, пока пользователь явно не изменит их.

## 1. Общая композиция и responsive UI

- Карта остаётся главным контекстом экрана.
- Bottom sheet не должен по умолчанию занимать половину экрана без необходимости.
- Варианты маршрута открываются в компактном состоянии примерно на треть экрана; детали доступны свайпом вверх.
- На планшете panel ограничивается по ширине и не растягивается на весь экран; в landscape допускается боковая/ограниченная панель.
- Меню, карточки и overlay не должны перекрывать друг друга или конкурировать за геометрию.
- Один контроллер владеет состоянием/геометрией конкретного экрана; motion-слой не меняет layout geometry.
- Переключения должны быть плавными и не оставлять кнопки временно недоступными/за пределами viewport.
- Обязательная матрица: compact phone 360x800 dp, обычный phone, font scale 1.25, tablet portrait 800x1280 dp, tablet landscape 1280x800 dp, API 26 и API 35, light/dark.

## 2. Остановки и станции на карте

Вместо одинаковых синих точек карта должна использовать разные интерактивные символы:

- автобусная остановка;
- трамвайная остановка;
- метро;
- МЦК;
- МЦД;
- железная дорога/электричка;
- пересадочный узел с несколькими видами транспорта.

Символы должны зависеть от zoom и не превращать карту в визуальный шум.

## 3. Нажатие на остановку/станцию

Нажатие на транспортный значок открывает один компактный bottom sheet, а не отдельное полноэкранное окно.

Карточка обязана показывать:

- название остановки/станции;
- типы транспорта;
- номера/названия маршрутов;
- направления движения и реальные конечные/headsign, если они присутствуют в данных;
- ближайшие отправления, когда расписание доступно;
- кнопку `Отсюда`;
- кнопку `Сюда`.

Поведение:

- `Отсюда` устанавливает выбранную остановку/станцию как точку A.
- `Сюда` устанавливает её как точку B.
- Если в одном месте есть несколько остановочных площадок/сторон дороги, пользователь сначала выбирает конкретную площадку/направление.
- После выбора площадки подсвечивается именно выбранная точка и соответствующее направление линии.
- Для радиальных маршрутов можно дополнительно показывать `в центр` / `из центра`, только если это вычисляется достоверно по реальному направлению.
- Для кольцевых маршрутов нельзя выдумывать `в центр`; показывается реальная конечная/следующая станция/направление движения.

## 4. Адресный поиск

- Обычные московские адреса, включая улицу, дом, корпус и строение, должны разрешаться локально без обязательного интернета.
- Нужен локальный адресный индекс: нормализованная улица -> дом/корпус/строение -> координата -> ближайший пешеходный вход/узел.
- Online geocoder используется только как дополнительный fallback, а не как обязательная часть основного сценария.
- Поиск остановок/станций также должен работать по локальному runtime.

## 5. Офлайн-маршрутизация и скорость

- Основной маршрут должен строиться без интернета при наличии установленного runtime.
- Обязательная цель первого полезного результата: 1-2 секунды.
- Первый маршрут показывается быстро; дополнительные альтернативы могут уточняться после первого paint.
- Обязательный CI-сценарий: airplane/offline mode -> два обычных московских адреса -> валидный первый маршрут <= 2 сек.
- Метро, МЦК, МЦД, наземный транспорт и пешеходные связи должны рассчитываться локально из runtime.
- Интернет используется для обновлений данных и optional fallback, но не является условием построения маршрута.

## 6. Пешая маршрутизация

- WALK должен использовать локальный OSM-derived pedestrian graph и точную route geometry.
- Нельзя рисовать прямую линию через здания, реки, железнодорожные территории, заборы или другие непроходимые препятствия.
- Если точная WALK geometry отсутствует, такой сегмент нельзя маскировать визуально как корректный прямой путь.
- Упрощение geometry должно сохранять повороты/форму; запрещено грубое равномерное прореживание, создающее срезанные углы.
- WALK, BUS, TRAM, METRO, MCC, MCD, TRAIN должны передаваться на карту отдельными GeoJSON feature/leg и иметь различимую стилизацию.
- Пеший сегмент отображается отдельным стилем (например, тонкая пунктирная линия), транспортные legs — своими цветами/линиями.

## 7. Активная поездка и GPS

- Пассажирский GPS двигает единый progress-engine по geometry маршрута.
- State machine не должна откатываться на предыдущий leg из-за пересечения линий/шума GPS.
- Верхняя карточка, compact mini-card и подробный sheet обязаны показывать один и тот же текущий GPS-этап.
- Обязательный GPS replay: WALK -> BUS -> transfer -> METRO -> WALK -> finish.
- Replay выполняется минимум на phone и tablet и сохраняет screenshots ключевых стадий.

## 8. Интерактивность и надёжность

- Быстрые повторные нажатия на поиск, настройки, tabs и route sheet не должны приводить к зависанию, потере window focus или дублирующим overlay.
- Interaction stress является обязательным CI gate.
- Ни один UI gate не должен считаться зелёным только потому, что build прошёл: обязательны runtime instrumentation и реальные screenshots.

## 9. Достоверность данных

- Нельзя изображать live-позиции транспортных средств без подключённого и авторизованного realtime-источника.
- GPS пользователя не должен выдаваться за GPS автобуса/трамвая/поезда.
- Направления, конечные, номера выходов и иные транспортные данные нельзя придумывать при отсутствии источника.

## 10. Критерий новой версии

Новая QA-версия выдаётся только после:

1. зелёной сборки/Kotlin/unit/Lint/APK verification;
2. зелёной responsive/device matrix;
3. зелёного GPS route replay;
4. зелёного interaction stress;
5. визуального просмотра свежих screenshots;
6. проверки компактных route/stop sheets без перекрытий;
7. проверки offline address + <=2 sec route gate после его реализации.
