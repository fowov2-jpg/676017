# ВремяХодом — обязательный чек-лист после изменения

Используется после каждого изменения кода, данных, конфигурации, CI, UX или ТЗ.

Допустимые статусы: **PASS**, **FAIL**, **NOT RUN**.

Нормативные документы, которые проверяются совместно:

- `docs/VREMYAHODOM_SPEC.md`;
- `docs/VREMYAHODOM_UI_QUALITY_CONTRACT.md`.

**Ключевое правило:** зелёный CI не перекрывает FAIL по продукту или UI. Наличие одного BLOCKER по визуальному контракту запрещает итоговый статус «готово» и запрещает выдавать APK как готовую версию.

### Правило адресного PASS

PASS по поиску адресов нельзя ставить только по наличию поля поиска или одному успешному адресу. Должны быть проверены разные формы адреса, включая корпус/строение/владение и нумерованную улицу. Номер корпуса или строения нельзя ошибочно принимать за базовый номер дома. Если адрес отсутствует во всех настроенных доверенных источниках, результат должен быть честным `не найден`, без выдуманных координат.

### Правило performance PASS

PASS по скорости маршрута нельзя ставить только потому, что маршрут когда-либо появился. Нужно отдельно проверить fast path и first-result contract. Полный background refinement может занимать дольше, но не должен блокировать первый пригодный маршрут. Увеличение timeout без устранения причины регрессии не считается исправлением.

### Правило визуального PASS

Для изменения UI статус PASS разрешён только после фактического просмотра результата рядом с применимым утверждённым референсом.

Зелёный instrumentation/emulator smoke, XML dump, наличие View, Espresso assertion или успешный запуск Activity сами по себе **не являются** доказательством визуального соответствия.

Для visual PASS обязательно проверить как минимум:

- общий силуэт и композицию экрана;
- долю карты;
- положение и размер поиска/быстрых действий;
- положение и размер bottom/side sheets;
- количество одновременно видимых карточек;
- отступы/скругления/тени;
- визуальную иерархию текста;
- стиль, размер, stroke и оптический вес иконок;
- структуру карточки «Рядом»;
- структуру вариантов маршрута;
- структуру активной поездки;
- отсутствие критического обрезания текста и пустых областей.

Если фактический скриншот получить невозможно, визуальный пункт получает NOT RUN с объяснением причины и риска. Если фактический экран существенно отличается от эталона без явного согласования пользователя — FAIL.

Если обычный пользователь сразу видит другой экран/другую композицию, отличие считается **BLOCKER**, а не «минорным».

Нельзя объяснять визуальный FAIL предположением («наверное эмулятор», «скорее всего MapLibre», «на устройстве будет нормально») без отдельной фактической проверки. Неизвестная причина остаётся неизвестной и не превращает FAIL в PASS.

### Правило normal-state

Эталонный populated-state нельзя закрывать тестом только loading/empty/error-state. Если референс показывает наполненную карточку «Рядом», список вариантов или активную поездку, для визуального PASS должен быть получен и проверен именно соответствующий наполненный экран.

### Правило отсутствия выдумок

Нельзя добиваться визуального сходства фиктивными пользовательскими данными или неработающими функциями. Тестовые fixtures допустимы только в явно тестовом сценарии и не являются доказательством реального product data-path.

Эталонные изображения и их SHA-256 закреплены в разделе 9 `docs/VREMYAHODOM_SPEC.md`. Дополнительные правила качества закреплены в `docs/VREMYAHODOM_UI_QUALITY_CONTRACT.md`.
