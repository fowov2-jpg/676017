# ВремяХодом — зафиксированное ТЗ

## 1. Продукт

Название приложения: **ВремяХодом**.

Назначение: городской маршрутизатор Москвы, который строит единый маршрут от двери до двери с учётом пеших участков и общественного транспорта.

Целевые режимы:

- WALK — пешком;
- BUS — автобус;
- TRAM — трамвай;
- METRO — Московский метрополитен;
- MCC — МЦК;
- MCD — МЦД;
- TRAIN — пригородные поезда/электрички.

Явно не поддерживаются: велосипеды, велошеринг, самокаты, электросамокаты, такси, каршеринг и речной транспорт.

## 2. Принципы маршрутизации

- Использовать реальное опубликованное расписание там, где оно доступно.
- Не придумывать отправления и ожидания для режимов, для которых нет достоверных данных.
- Пешие подходы, отходы и пересадки являются частью единого маршрута.
- Выбор транспорта зависит от фактического времени прибытия на пересадку.
- Поддерживать варианты: быстрее, меньше пешком, меньше пересадок/надёжнее.
- Допускается временно использовать слегка устаревший runtime для технического тестирования APK; это должно быть явно отделено от качества расписания.

## 3. Дизайн и UX

Референс — согласованные макеты из чата: карта является основным фоном, интерфейс строится поверх неё белыми плавающими карточками с крупными скруглениями и мягкой тенью.

Главный экран:

- строка поиска «Куда едем?» сверху;
- быстрые действия «Дом», «Работа», «Рядом»;
- карта на весь экран;
- нижняя навигация: «Карта», «Маршруты», «Транспорт», «Избранное»;
- плавающая кнопка настроек;
- карточки и результаты не должны закрывать карту целиком.

Экран вариантов маршрута:

- крупное суммарное время;
- время прибытия;
- пешие участки;
- транспортные участки с номером/линией;
- количество пересадок;
- несколько альтернатив по разным целям оптимизации.

Активная поездка:

- текущий транспорт и направление;
- ближайшие остановки;
- явное предупреждение, когда выходить;
- время до пересадки;
- постоянный статус поездки в приложении и foreground-уведомлении.

Настройки должны показывать только реально работающие функции. Нельзя выводить переключатель, который визуально меняется, но не влияет на приложение.

## 4. Брендинг

- Во всём пользовательском интерфейсе используется имя **ВремяХодом**.
- Старое пользовательское имя Human Router не используется.
- Launcher icon — загруженная пользователем иконка с часами, транспортом и буквами «ВХ».
- Внутренние package/namespace имена `app.humanrouter` могут временно сохраняться, если их изменение не даёт пользовательской пользы и создаёт риск миграции.

## 5. Технические ограничения

Нельзя ломать существующие рабочие компоненты без необходимости:

- runtime installer/updater;
- WALK graph;
- BUS/TRAM timetable;
- METRO/MCC routing;
- геокодинг;
- Android CI/signing.

MCD/TRAIN участвуют в Android-поиске только по опубликованному расписанию МТППК и только на проверенном участке Москва-Пассажирская — Зеленоград-Крюково. Остальная пригородная сеть остаётся недоступной до появления эквивалентных проверенных расписаний.

## 6. Критерий тестовой APK

Перед выдачей APK обязательны:

1. runtime integration smoke test;
2. проверка опубликованного runtime-current;
3. unit tests;
4. assembleDebug;
5. Android Lint;
6. проверка ZIP-целостности APK;
7. `apksigner verify`;
8. SHA-256 рядом с APK;
9. emulator/instrumentation smoke на поддерживаемых в CI Android API.

APK считается тестовой сборкой продукта только если устанавливается и отображается на устройстве как **ВремяХодом** с согласованной иконкой и новым UI.

Нельзя выдавать старый APK как результат новых изменений. APK должен быть собран из конкретного commit, содержащего эти изменения, и проверен тем же CI-прогоном.

## 7. Обязательный порядок после каждого изменения

После **каждого** изменения кода, данных, конфигурации, CI, UX или ТЗ исполнитель обязан завершить работу чек-листом по шаблону `docs/CHANGE_CHECKLIST.md`.

Правила чек-листа:

- каждый пункт имеет только статус **PASS**, **FAIL** или **NOT RUN**;
- **PASS** разрешён только при наличии фактического результата проверки;
- нельзя ставить PASS по предположению, только потому что код выглядит правильным;
- FAIL нельзя скрывать удалением, ослаблением или обходом теста без доказательства, что сам тест ошибочен;
- если исправляется тест, проверяемая продуктовая гарантия должна сохраниться;
- NOT RUN должен сопровождаться причиной и оценкой риска;
- после исправления ошибки необходимо повторно прогнать затронутые проверки;
- чек-лист должен отдельно указывать известные ограничения и незакрытые проблемы;
- перед выдачей APK обязательные проверки из раздела 6 не могут иметь статус FAIL или NOT RUN.

Минимальный чек-лист после изменения должен включать:

1. что именно изменено;
2. зачем внесено изменение;
3. какие файлы/компоненты затронуты;
4. проверка сохранения существующей функциональности;
5. unit tests;
6. Android Lint;
7. APK build/verification, если изменение затрагивает Android-продукт;
8. emulator/instrumentation smoke API 26 и API 35, если изменение может влиять на приложение;
9. профильные проверки для изменённой функции — маршрутизация, runtime, UI, безопасность, производительность или данные;
10. соответствие настоящему ТЗ;
11. известные ограничения/риски;
12. commit и CI run, которыми подтверждён результат.

## 8. Правила выпуска каждой версии

При каждом опубликованном APK/QA/release обязательно публикуется понятный человеку список изменений относительно **предыдущей опубликованной версии**, а не только номер commit.

Описание версии обязано содержать:

- номер версии;
- исходный commit;
- GitHub Actions run;
- раздел **«Что изменилось»** с функциональными изменениями;
- раздел **«Исправлено»** с исправленными ошибками;
- раздел **«Тестирование»** с фактически выполненными проверками и их результатом;
- раздел **«Известные ограничения»**;
- тип подписи APK: QA/debug или production;
- SHA-256 APK;
- ссылку/артефакт APK.

Изменения для release notes определяются по diff/commit history от предыдущей опубликованной версии до текущей. Нельзя писать в release notes изменение, которого фактически нет в выпускаемом commit.

QA/release не считается готовым, если обязательный чек-лист не закрыт или CI, требуемый для данной версии, красный.

После публикации версии исполнитель должен в чате показать краткий чек-лист выпуска и отдельно перечислить, что осталось невыполненным по ТЗ.

### 9.1. Приоритет эталона

При конфликте между старой реализацией, текстовым описанием, случайным Android-компонентом и этими изображениями для визуальной части приоритет имеют **эти эталонные скриншоты**, если пользователь отдельно не согласовал изменение дизайна.

Эталон определяет не только цветовую гамму, но и:

- композицию экрана;
- относительное положение поиска, быстрых действий, карты, карточек и нижней навигации;
- характер белых плавающих поверхностей, скруглений, теней и отступов;
- визуальную иерархию текста;
- стиль и размер иконок;
- расположение элементов управления картой;
- структуру карточки «Рядом»;
- структуру карточек маршрутов;
- структуру активной поездки и предупреждений;
- принцип сохранения карты как основного визуального фона.

### 9.2. Обязательная проверка UI после изменений

После каждого изменения интерфейса исполнитель обязан:

1. указать, какие эталонные экраны затронуты;
2. получить фактические скриншоты изменённых экранов с Android emulator/device, когда это технически возможно;
3. сравнить их с соответствующими файлами из `docs/ui-reference/`;
4. перечислить заметные отличия;
5. для каждого отличия указать: исправлено / допустимо по функциональной причине / требует согласования;
6. не ставить PASS по UI, если проверка фактически не выполнялась;
7. при существенном визуальном расхождении считать пункт соответствия ТЗ FAIL до исправления или отдельного согласования.

Изменение UI не считается завершённым только потому, что экран запускается и instrumentation-тест зелёный. Функциональный PASS и визуальный PASS являются отдельными проверками.

### 9.3. Правило изменения эталона

Эти файлы нельзя молча заменить новыми картинками. Изменение эталона допускается только по явному решению пользователя. При замене необходимо:

- сохранить новые файлы в репозитории;
- обновить этот раздел;
- обновить SHA-256;
- в changelog явно написать, что изменён визуальный эталон;
- сохранить возможность определить, какой эталон применялся к предыдущим версиям.
