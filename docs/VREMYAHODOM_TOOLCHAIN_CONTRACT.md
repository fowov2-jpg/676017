# ВремяХодом — обязательный контракт инструментов, доказательств и запрета выдумок

Этот документ является нормативным дополнением к `docs/VREMYAHODOM_SPEC.md` и `docs/VREMYAHODOM_UI_QUALITY_CONTRACT.md`. Он обязателен для разработки, QA и выпуска APK.

## 1. Базовый принцип

Цель инструментов — доказать соответствие согласованному продукту. Инструмент, плагин, SDK, зелёный CI, генеративная модель или удобство реализации не являются основанием менять ТЗ.

Запрещено:

- придумывать продуктовые функции, режимы транспорта, экраны, данные, остановки, адреса, координаты, расписания, отправления, ожидания или результаты маршрутов;
- добавлять функцию только потому, что её поддерживает подключённый сервис или SDK;
- подменять неизвестный факт предположением;
- объявлять PASS без фактического результата проверки;
- объявлять UI PASS только по instrumentation/CI;
- объявлять готовой APK при любом обязательном FAIL или NOT RUN;
- молча менять референс, тест или критерий ради зелёного результата;
- выдавать QA fixture/loading/placeholder/empty-state за нормальное рабочее populated-state;
- утверждать, что внешний сервис подключён к APK, только потому, что аккаунт/плагин доступен в ChatGPT.

Неизвестное или не проверенное состояние получает `NOT RUN` либо `FAIL` согласно риску. Предположение всегда явно помечается как предположение и не может служить evidence для PASS.

## 2. Иерархия источников истины

При конфликте применяется следующий порядок:

1. явное последнее решение пользователя;
2. `docs/VREMYAHODOM_SPEC.md`;
3. утверждённые файлы `docs/ui-reference/` для визуальной части;
4. `docs/VREMYAHODOM_UI_QUALITY_CONTRACT.md`;
5. настоящий документ;
6. проверенные опубликованные источники транспортных/адресных данных;
7. фактическое поведение текущего APK;
8. существующий код;
9. удобство реализации или возможности стороннего сервиса.

Старый код не имеет права отменять более высокий источник истины.

## 3. GitHub — источник кода, CI и артефактов

GitHub используется для:

- исходного кода;
- истории изменений;
- веток/commit;
- Android CI;
- тестовых логов;
- emulator screenshots;
- APK artifacts;
- SHA-256;
- release notes и опубликованных runtime artifacts.

Правила:

- каждое изменение должно иметь конкретный commit SHA;
- итоговый APK должен быть собран из того же commit, который проверен обязательным CI;
- зелёный CI подтверждает только те гарантии, которые реально проверяет соответствующий job;
- закрытый/зелёный workflow не является доказательством визуального совпадения;
- лог/артефакт конкретного run имеет приоритет над воспоминанием о предыдущем run;
- запрещено использовать старый APK как результат нового изменения.

## 4. Figma и `docs/ui-reference/` — визуальная спецификация

Главным визуальным источником истины остаются утверждённые пользователем изображения в `docs/ui-reference/` и их зафиксированные SHA-256.

Figma используется как измеряемое представление дизайна:

- размеры;
- координаты;
- spacing;
- радиусы;
- typography;
- цвета;
- иконки;
- reusable components;
- состояния экранов.

Правила:

- Figma не может молча заменить утверждённый screenshot reference;
- новый Figma-макет становится новым эталоном только после явного решения пользователя;
- если Figma и утверждённый reference расходятся без отдельного решения пользователя, приоритет у утверждённого reference;
- UI PASS ставится только после фактического сравнения Android screenshot с применимым reference;
- количественные измерения используются там, где они доступны, но не заменяют визуальную проверку композиции.

Из-за лимитов Figma MCP нельзя расходовать read-вызовы на повторное чтение неизменившихся экранов. Стабильные размеры/токены после подтверждения должны быть зафиксированы в репозитории, чтобы обычная разработка не зависела от повторного доступа к Figma.

## 5. Android Emulator и фактические screenshots — доказательство реализации

Эмулятор доказывает фактическое Android-поведение сборки.

Обязательные evidence для UI-изменения:

- screenshot именно из APK текущего commit;
- применимый reference открыт и просмотрен рядом;
- перечислены заметные отличия;
- BLOCKER-отличия исправлены;
- после исправления получен новый screenshot;
- проверены normal populated-state, а отдельно loading/empty/error-state, если они применимы.

Нельзя считать screenshot PASS, если на нём отсутствует содержимое, которое reference показывает как нормальное состояние продукта.

## 6. Sentry — crash/ANR observability, а не продуктовая логика

Sentry допускается только как диагностический инструмент.

Он не имеет права:

- менять маршрутизацию;
- влиять на выбор транспорта;
- подменять тесты;
- становиться обязательной сетевой зависимостью для нормальной работы приложения.

Если Sentry настроен:

- DSN хранится через конфигурацию/secret, а не через случайную вставку в UI;
- release должен содержать version и git SHA;
- `isSendDefaultPii=false`;
- адреса пользователя, точные GPS-координаты, полный маршрут и поисковые строки не отправляются как tags/breadcrumbs/custom context;
- screenshot/view hierarchy не включаются без отдельного решения пользователя;
- отсутствие Sentry/сети не должно ломать приложение.

Статус `Sentry active` разрешено ставить только после доказанного события/ошибки в соответствующем проекте, а не по одному наличию SDK в Gradle.

## 7. PostHog — продуктовая диагностика только при контролируемой телеметрии

PostHog используется только для агрегированной QA/продуктовой диагностики, если SDK фактически подключён к APK.

Допустимые события должны описывать действия и технические результаты, например:

- `app_open`;
- `search_started`;
- `search_result_shown`;
- `route_build_started`;
- `route_first_result_shown`;
- `route_build_failed` с ограниченным error code;
- `route_variant_selected`;
- `trip_started`;
- `trip_finished`;
- `settings_opened`.

Запрещено отправлять в аналитику:

- сырые адресные строки;
- точные координаты A/B;
- точную GPS-трассу;
- полный список посещённых остановок конкретного пользователя;
- персональные данные;
- содержимое поискового ввода;
- данные, позволяющие восстановить конкретный личный маршрут.

Для latency разрешены только числовые длительности и технические категории без личного содержимого.

Наличие подключённого PostHog-аккаунта не означает, что Android SDK интегрирован. `PostHog active in APK` = PASS только после фактически принятого тестового события из конкретной QA build/release.

## 8. Supabase — backend только для функций, закреплённых в ТЗ

Supabase разрешено использовать как backend только когда соответствующая функция явно утверждена в ТЗ.

Нельзя автоматически добавлять:

- аккаунты;
- облачную синхронизацию;
- социальные функции;
- серверное хранение истории;
- удалённое управление маршрутизацией;

только потому, что Supabase подключён.

Если функция действительно требует Supabase:

- схема создаётся миграциями;
- RLS/permissions проверяются;
- service-role key никогда не встраивается в Android APK;
- приложение должно использовать только клиентские publishable/anon credentials там, где это допустимо;
- security advisor проверяется после DDL/RLS изменений;
- backend failure не может заставить приложение выдумывать транспортные данные.

До появления утверждённой backend-функции Supabase считается доступной инфраструктурой, но не частью продуктового runtime.

## 9. Транспортные и адресные данные

Ни один внешний SDK/AI/backend не может быть источником выдуманных транспортных фактов.

Обязательно:

- использовать только утверждённые/проверенные источники;
- не выдумывать отправления, ожидания и позиции транспорта;
- не подменять неизвестный дом центром улицы;
- не выдумывать координаты;
- QA fixtures должны быть технически отделены от нормального runtime и не попадать в пользовательские результаты как реальные данные;
- источник, дата, checksum/schema и ограничения набора данных должны быть проверяемыми.

## 10. Реальные устройства и form-factor coverage

Минимальный автоматический Android gate:

- API 26 emulator;
- API 35 emulator;
- compact phone;
- large-text compact phone;
- tablet portrait;
- tablet landscape;
- GPS replay;
- screenshot artifacts для применимых UI состояний.

Реальное устройство пользователя является дополнительным доказательством, особенно для:

- launcher icon/label;
- touch/IME;
- GPU/MapLibre rendering;
- notification/foreground-service;
- layout на фактическом экране.

Ошибка на реальном устройстве не может быть отклонена только потому, что emulator CI зелёный.

Облачная device farm становится обязательной только после отдельного подключения/согласования. До этого нельзя писать `real-device cloud PASS`.

## 11. Доказательства и статусы

Любой обязательный gate имеет только `PASS`, `FAIL` или `NOT RUN`.

`PASS` требует конкретного evidence, например:

- GitHub run/job ID;
- commit SHA;
- log excerpt/artifact;
- screenshot текущей build;
- SHA-256 APK;
- Figma node/reference + измерение;
- Sentry/PostHog тестовое событие;
- Supabase query/migration/advisor result.

Фраза «код выглядит правильно» evidence не является.

## 12. Обязательный workflow после изменений

После изменения:

1. определить затронутые пункты ТЗ и references;
2. внести минимальное изменение без несогласованных функций;
3. запустить профильные unit/instrumentation tests;
4. собрать APK;
5. проверить integrity/signature/SHA-256;
6. выполнить API 26/API 35 и responsive gates, если применимо;
7. для UI получить реальные screenshots;
8. сравнить каждый затронутый screenshot с reference;
9. исправить все BLOCKER;
10. проверить данные/маршруты/адреса/latency по применимости;
11. проверить observability только если она реально интегрирована;
12. заполнить чек-листы PASS/FAIL/NOT RUN;
13. выдавать APK только при закрытых обязательных gates.

## 13. Release blocker

APK запрещено объявлять готовой, если выполняется хотя бы одно условие:

- UI существенно отличается от утверждённого reference;
- normal-state заменён loading/placeholder;
- есть выдуманные/непроверенные продуктовые данные;
- обязательный тест FAIL/NOT RUN;
- текущий APK не соответствует проверенному commit;
- launcher name/icon не проверены;
- адресный regression не закрыт, если затронут поиск;
- first-route contract не закрыт, если затронута маршрутизация;
- найденная пользователем реальная ошибка не воспроизведена/не классифицирована;
- release notes скрывают известное ограничение.

## 14. Правило работы AI/исполнителя

Исполнитель обязан:

- проверять факты инструментами, когда это возможно;
- отделять факт от предположения;
- не говорить, что работа выполняется в фоне, если фактической автоматизации нет;
- не считать проблему закрытой до проверки исправления;
- не оптимизировать CI ценой потери продуктовой гарантии;
- не добавлять сторонние сервисы без конкретной пользы;
- не использовать сервис как оправдание изменения UX;
- при сомнении оставлять статус незакрытым, а не придумывать PASS.
